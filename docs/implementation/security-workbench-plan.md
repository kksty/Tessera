## 1. 产品定位与已确定的取舍

Tessera 是安全测试专项工作台。保留 FGS 驱动的自主探索，以及范围授权、原始证据、独立审核、漏洞库、风险统计和报告能力。Cairn_Y 用于校准搜索机制，不作为逐项复刻的功能清单。

已确定的调整：

1. 继续使用 Pi 完整会话 SDK，保留上下文管理、会话持久化、自动压缩、模型协议、重试和事件。Tessera 控制任务提示词、自动资源加载、工具权限与业务状态。
2. Decide 负责规划，Execute 负责观测和行动；Review 保留为证据审核活动，与前两类任务共用运行器。Review 不自行复测目标，需要复测时交由 Decide 创建普通 Step。
3. Fact 保存带条件的观测；Finding 保存值得独立管理的安全测试结论，包括候选漏洞和信息类结论。普通指纹、响应和失败记录按问题需要保留为 Fact，不为增加数量创建 Finding。
4. 信息类 Finding 可以审核通过并长期保留。只有当前版本审核通过、具有证据和有效影响评分的漏洞进入漏洞库、风险统计和漏洞报告正文。
5. 优先补齐因果查询、审核调度与结束语义，随后压缩提示词并评估收益。继续复用现有租约、版本检查、事件、outbox 和不可变证据。
6. Decide 自主决定工作图节点的保留与删除。删除是通用规划动作，适用于无关、过时、重复、错误、已放弃或不再值得保留的材料，不限于网络配置故障，不要求人工先发 Hint、再次确认或由 Review 批准。服务端保证引用与运行状态一致，不替模型审核删除是否明智。

本轮不建设通用任务插件、任意 Finding Schema 引擎或专家 Agent 系统；不重写 Agent Loop，不修改 Pi 安装包源码。

## 3. Pi 的职责与提示词边界

### 3.1 保留会话 SDK

继续使用 `createAgentSession`、`SessionManager`、`SettingsManager` 和受控 `DefaultResourceLoader`。普通 Run 创建新会话，跨 Run 的业务事实来自 FGS 和项目工作区；只有明确的原 Run 只读恢复打开原会话。

Pi 负责当前 Run 的消息历史、压缩、请求和工具往返。压缩摘要属于会话材料，不能自动提交为 Fact、Finding 或 Evidence，也不能代替当前资产授权。

### 3.2 业务系统提示词只由 Tessera 提供

- 把系统提示词与环境附加内容的构造集中到一个 Runner 模块，供运行、导出和测试共用，避免导出脚本自行重组出另一份“最终提示词”。
- 保留显式非空 `systemPrompt` 和显式 `appendSystemPrompt` 数组；禁用自动发现的资源类型，加载结果也必须为空。无环境文件时使用受控简短回退。
- 使用当前 SDK 的公开配置边界；如改用 `systemPromptOverride`、`appendSystemPromptOverride`，回调只能返回 Tessera 的内容，不拼接 loader 的默认结果。
- 去掉默认 coding 身份、通用编程工作流、Pi 自身教程入口以及自动项目指令注入。保留实际工具声明、工作目录、必要环境信息和平台任务约束。
- 不批量删除工具说明、结果修复契约或压缩提示。这些内容应按用途审查，不能通过空字符串破坏 SDK 的正常功能。
- 默认压缩如在实测中遗漏测试前提、证据 ID、范围限制或未完成问题，再通过 SDK 支持的摘要定制边界调整。禁止直接修改 `node_modules` 或把压缩摘要写回共享事实图。

验证对象包括首次任务请求、压缩后的首次请求、结果修复及只读恢复。检查模型实际接收的系统消息和工具集合，不只检查初始化参数或静态关键词。测试材料不得读取、输出用户全局凭据。

主要修改位置：`packages/runner/src/run.ts`、新的提示词构造模块、`scripts/export-prompts.ts`、`tests/runner/runner.test.ts`。保留 `packages/models/src/runtime.ts` 的供应商解析和压缩设置归属。

## 4. Fact、Finding 与漏洞入库

### 4.1 明确三者含义

| 对象 | 应保存的内容 | 通过或失败的含义 |
| --- | --- | --- |
| Fact | 访问结果、测试条件、异常、反证、失败与可复用线索，附原始证据和来源 | 记录观测状态；不承诺模型解释一定正确 |
| 信息类 Finding | 对当前评估有独立价值、可核查的结论或加固建议，明确适用范围 | 审核确认该信息结论成立，不表示存在漏洞 |
| 漏洞类 Finding | 声明安全边界受损，描述前提、机制、影响与复现材料 | 审核当前版本的漏洞声明与影响证据 |

项目通过既有 goal 和 Hint 表达交付范围，不新增一套通用定义语言。例如，普通服务版本默认留 Fact；与本项目评估目标直接相关、需要在交付中单列的暴露面结论可以成为信息类 Finding。

### 4.2 分类与危险度分开

给 Finding 增加 `kind: "vulnerability" | "informational" | null`，Review 记录也保留当次分类。Execute 可以提出分类；只有当前版本审核通过后的分类才可作为确认结论。`null` 表示尚未确定，不能根据“不是信息类”反推为漏洞。

- 漏洞类通过：明确 `kind=vulnerability`，具有引用证据、有效 CVSS v4.0 vector、程序计算的正分，以及当前要求的影响证明。
- 信息类通过：明确 `kind=informational`，具有足以核查信息结论的证据；当前危险度与 CVSS 为空，不要求填写不存在的漏洞影响。
- `needs_evidence` 和 `rejected` 都不进入漏洞库。缺少评分不等于信息类，信息类也不等于被驳回。
- 新写入以 `kind` 分类；当前不从历史危险度或评分推断类型，也不提供旧库转换或启动迁移。缺少明确分类的记录不能仅凭旧 pass 进入漏洞库。
- 合并或实质修订仍创建新版本并复审；本轮不新增“模型判断改动不重要即可沿用旧 pass”的捷径。

收敛一个服务端入库谓词，概念上同时要求：

```text
kind = vulnerability
且当前版本审核通过
且 Finding 本身未合并、未撤回、未驳回、未删除
且具有引用证据和有效的当前 CVSS / 影响证明
```

前端、总览、导出和报告使用同一服务端结果或同一纯函数契约；不能各自维护不同的“已确认漏洞”定义。

### 4.3 保留信息，纠正撤回与编号

- 删除“一旦只有观测或加固意义就必须撤回”的全局要求。撤回用于无独立交付价值、重复或超出项目明确交付范围的结论；证据反驳某项声明则使用审核驳回。
- 信息类审核通过后仍可查询、导出和回溯，默认退出风险统计和漏洞报告正文。报告可另设信息与建议附录，不混入漏洞数。
- Finding 撤回或驳回不删除来源 Fact、原始证据或历史版本。不能仅因某条不是漏洞，就把底层观测标为 disputed。
- 已撤回结论出现新的有效依据时，允许明确恢复为新版本重新审核，保留撤回历史。禁止同身份增量提交被静默吞掉，或仅靠换 ID 绕过撤回。
- `v001` 等继续作为所有 Finding 的稳定编号。不得按类型、审核结果或漏洞入库情况重编号，也不硬编码从 `v007` 开始。

工作台项目内入口改为“发现”，展示全部有效 Finding 和审核状态；全局“漏洞库”只展示满足入库谓词的漏洞，候选、信息类与驳回记录在发现入口查看。“入库”指进入漏洞集合，所有类别仍需持久保存，不另复制一份业务记录。Decide 可按 5.2 自主删除节点；被删记录退出默认工作列表，原文与审核历史保留在显式历史入口，不因持久保存而继续进入活动图。

主要修改位置：`packages/protocol/src/{schemas,models}.ts`、`packages/core/src/{store,overview,report-material,finding-merges}.ts`、`packages/runner/src/prompts.ts`、Web 的发现、审核、漏洞库、总览、报告和筛选组件。

## 5. 因果查询与工作图维护

### 5.1 补齐因果查询和来源

Fact 新增可选 `step_id`、`run_id`、`created_at`，新观测由服务端从有效租约填写，不能信任模型自报生产 Run。原始 Evidence 继续不可变。

生产来源只使用服务端记录的 `step_id` / `run_id` 或明确保存的生产关系；缺失时保持未知，不从 `Step.fact_ids` 反推历史归属，也不把 Step 的最近 Run 当作旧 Fact 的生产 Run。`origin` 或人工导入的无生产 Step 记录允许无该关联。原 M1 阶段曾有旧关系兼容推断，当前已移除该路径。

查询语义统一为：

- Fact 的上游包含生产 Step 及直接 Evidence；继续一层可到达该 Step 的 `from` Fact。
- Step 的上游为输入 Fact，下游为产出 Fact 及关联 Finding。
- Finding 的上游为来源 Fact 和直接 Evidence；Review 的上游为被审核 Finding 版本。
- 下游查询与这些边的反向关系一致。Evidence 引用和生产关系分别返回，避免把证据引用误说成生产过程。
- 保留深度上限、去环、稳定排序和分页快照契约；较深链路可从返回的边界继续查询。

查询、Execute/Review 投影、图展示与报告溯源共用来源解析函数。重开同一 Step 时保留每次 Run 的产出，不把旧事实归给最近一次 Run；争议状态更新有事件，不覆盖原始证据。

验收覆盖 `origin → s001 → f001 → s002 → f002` 双向查询、多个来源、未知来源保持未知、重开多 Run、直接证据、分页与循环防护；测试预期随当前来源契约维护。

M1 当前实现：`packages/protocol/src/graph-relations.ts` 统一解析带类型的边与明确生产关系，查询结果的 `relations` 与 `provenance` 分开表达依赖、生产和证据引用；Review 边保留所审核的 Finding 版本。关系查询保持 1–3 层、去环、稳定排序及快照游标，深链从边界 ID 继续查询。新 Fact（含运行内资产发现产生的观测）由服务端绑定有效 Step/Run，并记录时间；人工观测可有 Step 而无 Run。明确保存多个生产关系时可表示歧义，字段缺失则不猜测、不补最新 Run，也不改变已读水位。

Execute/Review 的直接 Fact 带生产信息及生产 Step 的输入索引；黑板、详情和报告使用同一解析器。新报告冻结完整上游 Fact、Step 关系与所需证据；旧报告缺少 `trace` 时仍按原内容读取，新旧材料结构不同可能使旧报告显示过期。回热、冷却和读取元数据不改变报告材料，源事实争议则会使新报告材料变化。

主要修改位置：`packages/core/src/{memory,projection,store,report-material,reports}.ts`、`packages/protocol/src/{models,graph-relations}.ts`、Runner 的查询说明、Web 的黑板/详情/报告及 `tests/core/graph-relations.test.ts`。

### 5.2 Decide 自主删除节点

#### 改造前的缺口与实施依据（功能已完成）

**可行，纳入实施范围。** 模型既然承担规划，也应能决定哪些节点不再属于当前工作图；不因担心模型删错而把删除收回为人的专属操作，也不设置只能删除网络异常、失败观测或低价值节点的白名单。Hint 可以改变删除判断，但不是授予删除权限的前置条件。

以下缺口对应 `101b9c9` 改造前源码，现已由 M1D 落实：当时 Decide 能废弃未关闭 Step、修订/撤回 Finding、调整子 Goal 和冷却资产，但不能通用删除 Fact、已结束 Step 或其他探索节点。Review 的 `disputed_fact_ids` 只标记争议；资产冷却、Fact 争议、Step 关闭和 Finding 撤回也都不等于删除工作图节点。该历史差异解释了为何需要成套实现，不能继续列为当前缺失功能。

M1D 复用 SQLite 事务、Decide 计划/结算、Run 取消、不可变 Evidence 和事件记录，实现了以下完整契约：活动投影与检索过滤、持久删除标记与稳定编号、增量事件及前端回放一致。原文和历史保留，当前工作图退出；没有新增 Agent 或人工审核流程。

#### 能力与提交契约

在既有 `submit_decisions` 中增加 `delete_nodes`，由 Decide 自主批量提交，例如：

```json
{
  "delete_nodes": [
    { "id": "f012", "reason": "与当前目标无关，无需继续保留", "cascade": "none" },
    { "id": "s004", "reason": "放弃该分支及其后续推导", "cascade": "downstream" }
  ]
}
```

- 对 Fact、Step、Finding 和模型创建的子 Goal 开放；既能删除进行中的节点，也能删除已结束或已审核节点。`reason` 是模型对自身决策的简短记录，不是交给服务端或人的证明材料。
- `cascade=none` 为默认，只删除所列节点；`downstream` 按 5.1 的生产与依赖关系扩展删除所有可达后继，包含 Step 产出、消费这些 Fact 的 Step 及关联 Finding。后继即使还有其他有效来源也会被删除，程序不因多来源而自动保留。删除子 Goal 时，其关联 Step 属于可扩展关系。模型可以显式批量列出任意组合，不要求先证明节点无引用；要保留共享后继，应改用 `none` 并明确列出删除集合。
- 级联只沿业务依赖边向下展开并去环，不沿同资产、同关键词或共用 Evidence 扩散，不反向删除仍可能有用的前提。实际删除与受影响节点列表在预览和结算中返回。
- 删除前用 `preview_deletions` 只读查看完整删除集合、受影响的保留节点、取消 Run，以及 `shared_descendants` 中仍有其他保留依赖的后继。预览复用正式删除解析，不写图或业务记录、不推进已读水位。Runner 只接受已在前一次模型响应中返回、与本批 ID/理由/级联方式匹配的有效预览，不允许在同一工具批次中预览后直接提交。运行器自动携带影响指纹，服务端在结算中重新比较；范围或取消目标变化时冲突并要求重新预览，已提交的新计划保留。该步骤是模型读取操作后果，不引入人的确认、Review 审批或服务端价值裁决；旧直接 API 调用兼容不带可选指纹。
- `origin`、人工根目标、Hint 和资产授权属于任务与权限输入，仍走对应专门接口；Evidence、Review、Run 属于原始或历史记录，保留既有生命周期。这里定义的是探索工作图的自主编辑范围，不把探索节点删除变成改写人的目标或销毁原始记录的入口。
- 沿用 Decide 的租约、已读快照和幂等提交契约。并发导致快照过期时返回冲突与当前视图，由模型刷新后重新提交；不增加人工确认、Review 审批、复测证明或等待任务自然结束的步骤。

#### 删除的实际效果

删除后，节点立即退出活动工作图、默认 Decide/Execute/Review 投影、冷热池、普通查询/全文检索结果、默认图展示、调度和当前交付统计。不能只折叠、降低优先级、设置 `disputed` 或移进冷区，再让后续 Decide 反复读到同一正文。

持久层采用统一删除标记，保留原 ID、原文、删除时间、操作者、Decide Run、提交键与理由；历史详情明确显示“已删除”。删除标记及相关变更写入事件，回放到删除前仍能看到原图，删除后按相同活动节点规则呈现。历史通过显式历史读取或审计导出访问，不自动混入工作图和模型入口。保留历史是复用现有追溯机制，不是要求模型以后重新处理这些节点。

只删除一个节点，不自动断言其内容错误，也不把删除 Finding 等同于 Review 驳回。删除工作记忆与反驳事实是不同动作：模型若认为旧材料导致其他结论不成立，应显式删除相关 Finding 或修订其声明/证据，不能由服务端仅按“引用过这个 Fact”推导出结论错误。已存在的证据、历史审核和冻结报告继续保留；当前漏洞库与新报告排除被删 Finding，报告材料实际变化时标记旧报告过期。删除 ID 永不复用；新观测需要新节点时分配新编号。

避免旧内容从旁路回流：

- 保留节点引用已删除节点时，来源解析返回“来源节点已删除”的明确标记与历史定位，不复述其正文，不无提示地移除引用、伪装成完整推导；已删节点不再作为新计划的活动 Fact 来源。既有 Step 不因关联引用而自动暂停、废弃或重建，是否继续由 Decide 决定；删除本身不因存在引用而失败。资产授权仍沿持久的来源关系校验，不能因工作图隐藏节点而丢失范围限制。
- 保留 Finding 及其已有原始证据、当前声明没有改变时，不因来源 Fact 退出工作记忆而自动加版本、撤销 pass 或强制复审。模型显式修改声明/证据时，按 M2 的新版本/复审契约处理；模型删除 Finding 时，直接退出当前交付。服务端不据拓扑关系自行判定漏洞失效，也不自行新建复测 Step。
- 默认投影不再复述被删内容；生产 Step 的摘要若可能包含被删产出，入口改给“部分/全部产出已删除”的索引与仍有效 Fact ID，原摘要留在显式历史读取。书签、变化索引和冷预览不得从历史事件重新注入被删正文。仅由已删节点引用的 Evidence 和历史 Review 不再作为默认图检索的推荐或命中材料，仍可按原 ID 显式读取；共用且仍支撑有效节点的 Evidence 不受连带删除。
- 仅当 Step 本身在明确删除集合中，或 Finding 本身在删除集合中且正在审核时，在同一结算中终止对应 Run 租约，Dispatcher/Runner 随后取消其工作。显式 `downstream` 扩展得到的集合按同一规则处理。单独删除 Fact 不自动取消其生产/消费 Run；要结束正在扫描的分支，Decide 应同时删除/废弃该 Step，或明确选择下游级联。
- 已在执行的外部请求不能保证撤销。被取消的旧 Run 不得再新增写入；任何 Run 都不得通过更新已删 ID 或重放增量内容使节点自动恢复，已接受的原键回执仍可重放。其他保留 Run 可继续提交新的观测，服务端不按文本相似度把它们擅自判成应删除的旧内容。
- 运行中的模型已经读到的上下文不会因数据库变化自动消失，不能承诺删除能擦除所有在途会话的历史。已被取消的 Run 后续重开时使用删除后的新视图；其他 Run 按既有刷新/读取契约观察变化。提交删除的 Decide 按现有提交成功即结束的规则退出，下一轮 Decide 从删除后的干净上下文开始。

#### 事务、结束语义与提示词

明确删除集合、来源标记、被删 Step/Finding 的 Run 终止及索引处理属于同一次结算的原子业务动作；失败不得出现“Finding 已删却仍计入漏洞”或“图已删但默认检索仍命中该节点”的中间结果。FTS、冷热池、图展示和报告共用活动节点判定，历史查询另行显式选择。不能借一致性处理扩大成服务端自动裁决其他节点是否有价值或是否错误。

继续保留现有“计划先提交，结算冲突不回滚计划”的契约。计划阶段应交叉检查同批新 Step 与声明的删除范围，不创建依赖待删除节点的新任务；结算时重新检查并发状态。删除与同批更新、合并、重开冲突时按既有结算冲突返回，不把执行顺序交给客户端猜测；已经提交的新计划不因后续删除结算失败而偷偷回滚。

节点删除是规划变化，须清除不再成立的完成提议，并纳入 M4 的规划水位分类。同批 complete 依据删除后的未关闭工作和审核状态校验；模型请求的级联展开结果需要明确返回，不能借删除推进模型未读内容的已读水位。M4 落地前也须使用现有观测/结算契约使旧完成提议失效，不能只在前端隐藏节点。

Decide 提示词明确允许自主删除，简要说明批量与级联、删除后不再作为依据，以及读快照/冲突的接口契约。示例应覆盖无关信息、探索方向变化、重复材料、过时前提和错误判断，不把删除教程写成“只有确认环境故障才允许清理”。Execute/Review 继续通过观测和审核表达结果，工作图保留取舍由 Decide 决定。

M1D 当前实现：`node-lifecycle.ts` 统一活动图与删除引用，`node-deletion.ts` 负责明确集合、下游扩展和原子结算，复用既有租约与回执。只删除明确集合，不自动裁决其他结论失效。删除保留原文和编号，在首次删除时写 `node_lifecycle_version: 1`；旧 format-1 记录没有删除标记时保持原状，不自动转换数据或补已读水位。默认入口、检索、书签/变化索引、图和交付过滤共用活动图；被删生产来源返回标记，授权沿持久图校验。显式历史和事件保留，查询结果不自动复制为新 Evidence。删除按业务变化检查快照，普通用量记录不误触发冲突；同批 complete 使用删除后的工作状态，仍沿用现有完成机制，规划水位拆分留待 M4。

2026-10-19 后果补全：明确多来源后继仍在级联范围内，模型通过 `preview_deletions` 查看完整影响后再提交；Runner 阻止缺失/不匹配预览及同批工具绕过，服务端复核可选影响指纹。预览与结算共用依赖展开、取消目标解析，预览不生成新 Evidence，不自动承认新的 Hint 或观测。

主要修改位置：`packages/protocol/src/{schemas,models,node-lifecycle,work-events}.ts`、`packages/core/src/{node-deletion,decisions,store,memory,memory-changes,projection,history,search,overview,report-material}.ts`、`packages/runner/src/{run,prompts}.ts`、Dispatcher 取消处理及 Web 的图、详情、历史、统计和报告入口。实施验收见第 12 节。

## 6. 调度：及时规划，限制审核占用

保留全局与单项目总并发上限，增加单项目审核并发上限，默认 1；有效上限不得超过项目总并发。已有运行不因改策略而被抢占。

下一可用槽位的领取规则：

1. 项目处于可运行状态，先执行现有租约清理、资产、恢复阻塞和重试门槛检查。
2. 有到期且未在运行的 Decide 时优先领取一个 Decide。继续合并流式变化并保留最大等待窗口。
3. 没有可领取 Decide 时，在可执行 Step 和可审核 Finding 之间轮换；只有一类可运行时直接领取该类。
4. Review 达到项目审核并发上限后不再领取；有空余资源且存在 Execute 时继续执行。
5. 总并发为 1 时也要在 Execute 和 Review 都持续就绪的情况下交替推进，避免一类永久饥饿。轮换记录不得改变业务观测水位。

Review 在当前可领取集合内按 Finding 编号数值升序选择，不能使用字符串排序处理 `v999 / v1000`。已审核当前版本、在审、合并、撤回、未完成来源任务、资产未批准或处于退避的条目按现有门槛跳过。恢复可领取后重新参与排序。

编号顺序决定领取顺序，不保证并发完成顺序。审核记录页面仍可以按完成时间最新在前展示，待审核列表应与后端可领取顺序一致并显示跳过原因。

Dispatcher 继续按项目分配资源，检查跨 tick 的项目轮换，避免固定列表头部项目反复抢到唯一空位。这里承诺“下一可用槽位优先规划”，不承诺长任务尚未释放资源时仍能立即启动 Decide。

主要修改位置：`packages/core/src/store.ts`、`apps/dispatcher/src/loop.ts`、运行配置与设置页，以及调度、退避和租约回归测试。

## 7. 搜索结束与交付完成

保留外层 `project.status = active | stopped | completed`，不为本轮增加一套可独立写入的多阶段工作流。UI 额外展示从业务记录派生的“探索进行中 / 搜索结束、审核中 / 已完成”。暂停仍阻止所有自动领取。

### 7.1 规划水位独立于普通交付变化

新增 `Graph.planning_revision`、`Graph.decided_planning_revision`，完成提议记录模型实际看到的 `planning_revision`。原 `revision`、`observation_revision`、`decided_revision` 继续承担原有快照、事件与提交契约，不通过推进这些旧水位让模型自动承认未读材料。

以下变化推进规划水位、触发 Decide，并使旧搜索完成提议失效：新的或被纠正的 Fact、Step 执行结果与重开、目标/Hint/授权范围的有效变化、Finding 新增或声明/证据变化、负面审核结果、源事实被争议、节点删除，以及需要重新规划的执行失败。当前 Decide 自己提交的删除按 5.2 的结算与已读契约处理，不能自动承认级联展开中的未读变化；删除本身不推导出其他结论失效。

普通 Review pass 仅确认当前版本、记录分类和评级，且没有新增反证或实质声明变化时，更新交付状态，不独立触发一轮 Decide。Review 如果同时提出需要处理的新问题，应以明确的审核问题字段进入规划变化，不能藏在 pass 的评分说明中。

Run 心跳、用量、读取回热、书签和展示筛选不推进规划水位。把事件分类集中实现并逐项测试，不能只靠事件名称或“所有 review 都不重要”的假设。

### 7.2 完成提议与最终完成

- Decide 基于实际读到的最新规划水位提出 complete；必须结论化或放弃未关闭 Step、回应有效 Hint，并给出目标达成或评估停止理由。
- 搜索完成提议可在仍有 Review 时成立，UI 显示“搜索结束、审核中”；此时项目仍为 active，可继续领取已有交付审核。
- 普通 pass 不清除该提议。出现负面审核或其他规划变化时，清除提议并唤醒 Decide，由其决定补证、纠正、撤回，或承认不足后结束。
- `needs_evidence` 不要求无限复测。Decide 读到该结果后，可以规划验证，也可以说明现有缺口与停止理由；该 Finding 保持未确认，不入漏洞库，交付披露未解决项。
- 只有有效搜索完成提议仍覆盖最新规划水位、没有未完成搜索工作、没有在途 Decide/Review，且应审核的当前 Finding 版本均有结果时，才把项目设为 completed。
- 改写目标、加入新 Hint 或明确重开会使搜索状态重新开放。完成或暂停的项目不能通过普通旧 Run 补交恢复行动；沿用已有幂等回执与租约检查。

迁移旧项目时不得自动补齐“模型已读”的水位，也不把旧完成提议直接升级为新有效提议。需要在恢复运行后的下一轮 Decide 基于新投影重新确认。

主要修改位置：`packages/core/src/{store,decisions,history,projection}.ts`、协议、Runner 的实际投影视图与提交封装、Dispatcher 状态处理及项目总览/时间线。

## 8. 提示词与上下文调整

在前述契约稳定后精简提示词，保持三类活动的权限和目标清晰：

- 公共部分只保留范围授权、Fact/Finding/Evidence 的区别、原始材料原则、共享状态与输出语言。
- Decide 聚焦目标、未完成问题、有效 Hint、来源关系、已执行结果和需要处理的审核问题；事务冲突与字段含义优先由 Schema 和工具返回解释。
- Execute 聚焦当前问题、输入条件、已获准行动、增量事实与必要 Finding。信息类结论不强制写漏洞影响；CVSS 的最终填写留给漏洞审核。
- Review 聚焦结论类型、证据是否支持声明，以及漏洞的影响、前提和 CVSS。明确它是已有证据审核，复现测试属于 Execute。
- 不在多个位置重复整套合并、撤回、评分与检索教程。按需资料继续是只读参考，不作为新事实或攻击流程。

保留冷热投影与全文检索，先补当前 Step 及未解决审核问题的直接因果依据；源记录全文仍可按需读取。入口需要记录实际长度与模型用量，不把200个节点当作 token 预算。超长未关闭工作提供精确索引和分页，投影器不擅自省略问题或截断关键限制；Decide 显式删除的节点按 5.2 退出默认投影和检索，不受该保留规则强制回填。Pi 自动压缩继续负责 Run 内消息。

增补无明显关键词、跨多个 Step 的前提、矛盾事实、重开与权限变化场景，评价模型是否选择了正确查询并读到原文，而不只测试某 ID 在接口上可检索。

## 10. 数据兼容、部署与回退

当前只接受 `format_version: 1` 持久图，不提供旧库转换工具或启动迁移；原 M2 阶段的转换试验只保留为历史验收记录。当前读取和发布遵循以下契约：

- Finding 分类以明确的 `kind` 为准，不从历史危险度、零分或旧 pass 反推。缺少当前分类、证据或合法影响评分的记录保留原文，并退出已确认漏洞集合。
- Fact 生产来源只用明确记录的 Step / Run；缺失保持未知，不从 `Step.fact_ids` 猜测，不补最新 Run 或模型已读水位。
- 节点缺少删除标记时按未删除读取；删除标记、稳定编号、历史事件与原件不因索引重建而丢失。索引是派生数据，可以重建；重建不等于迁移业务记录。
- Server、Dispatcher、Runner 和 Web 按同一业务契约发布。镜像标签不足以证明同版，应保留构建 / 镜像 ID，排空旧任务后再更新项目容器，避免旧运行器继续提交不匹配的协议。
- 备份同时覆盖平台 SQLite 一致性副本、原始证据和项目工作区。回退检查代码与持久契约是否兼容；需要恢复数据时使用匹配备份，并另行保全切换后产生的原始产物。冻结报告和证据不由回退操作自动改写。

本轮没有新增正式数据转换或切换安排。后续若确需支持其他数据格式，应作为独立变更设计、验证和交付，不能从本文历史迁移段落推导出当前已有能力。
