# 两种并行架构：决策者架构与蜂群架构

Tessera 同时提供两种任务架构。它们**并行存在、按项目隔离**，不是新旧版本，也不是“先进/落后”的关系。

|            | 决策者架构                                            | 蜂群架构                                                  |
| ---------- | ----------------------------------------------------- | --------------------------------------------------------- |
| 持久化值   | `project.mode = "classic"`（缺省）                    | `project.mode = "swarm"`                                  |
| 规划位置   | 单一 Decide 读图、定方向、开 Step                     | 每个 peer 自己决定方向与方法                              |
| 执行上下文 | 每个 Step 单独执行，结果交回图                        | 每个 peer 一条持久会话，规划与执行不换上下文              |
| 协调方式   | Step 队列 + 图 + Review                               | peer 消息 + 图 + 共识轮次                                 |
| 完成判定   | Decide 判断 + 覆盖表 + 审核/Hint 门槛                 | 全体在岗 peer 共识 + 覆盖表 + 审核问题处置（Hint 不阻塞） |
| 适合       | 资产测绘、合规扫描、SCA、边界明确或可并行的独立子任务 | 未知状态、线索互相依赖、单点突破、需要连续上下文的探索    |
| 不适合     | 需要频繁现场改向、把利用链切碎会丢线索的任务          | 需要全局统一优先级、强一致队列或大规模确定性流水线的任务  |

两种架构共用同一套 FGS 黑板、Evidence、Review、Hint、完成覆盖表、报告和 UI。差别只在**控制面**：一个把规划放在单一入口，一个把规划放回每个执行者。

## 蜂群开单：明确写入 `mode: "swarm"`

蜂群不是“运行起来以后再切”的模式；它在**创建项目时**选定，之后不可切换。

### Web

新建项目 → 「架构模式」选择 **蜂群架构 · 平等执行者（Swarm）**。创建请求会把 `mode: "swarm"` 写入项目记录。

### API

```http
POST /api/projects
Content-Type: application/json

{
  "title": "示例项目",
  "origin": "https://example.test",
  "goal": "评估目标",
  "mode": "swarm"
}
```

`mode` 缺省为 `classic`。要开蜂群单，必须显式传 `"swarm"`；不要依赖标题、描述或 UI 徽章推断模式。

## 蜂群内部的两种运行形态

创建蜂群项目时，服务端会放入一个初始 peer（`p001`），状态为 active。此时有两种用法：

### 单 peer：连续单 Agent

不调用 `spawn_peer`。只有一个 peer 在自己的持久会话里连续规划、执行、观测、再规划。

- 没有 Decide，没有 Step 队列；
- 没有 Planner → Worker 的交接；
- 最接近“一个模型从头到尾探索”的连续 Agent；
- 适合单点突破、未知状态、线索需要留在同一上下文里的任务。

单 peer 下“全员共识”退化为自我同意，但 Finding 仍必须经过独立 Review。

### 多 peer：并行探索 + 消息协调

peer 可以调用 `spawn_peer` 裂变出同伴，通过 `send_message` / `read_inbox` 协作，通过 `retire_peer` 退出。

- 适合可以真正并行的方向；
- 代价是上下文被切分，消息如果只传结论、不传证据，后来者只能继承判断；
- 因此多 peer 只在“并行收益大于交接损失”时使用。

`spawn_peer` 由在岗 peer 发起；全部退休时，操作员可在执行者页补位。所有在岗 peer 等待至少五分钟且没有可领取工作时，执行者页提示检查并手动唤醒。

## 负向结论：两种架构共同遵守的边界

无论决策者架构还是蜂群架构，`not_observed` 都只表示**在 `negative_scope` 范围内未观测到**，不等于“方向已穷尽”或“已证伪”。

新的负向 Fact 必须携带：

- `request`：产生该结果的精确请求（method/url）；
- `parameter_sources`：每个 URL 参数的来源；
- `negative_scope`：`attempted`（试过什么）、`not_tested`（没覆盖什么）、`confidence`（low/medium/high）。

缺范围或溯源的负向提交会被服务端拒绝。`conclusion` 不应写“已证伪/已穷尽/系统性排除”这类无范围判决；措辞由模型与审核判断，不以关键词硬拦截；单次未观测只能写成“本次未观测（范围：…）”。Review 和 Decide 读取负向 Fact 时，必须按范围理解，不能把一次失败升级成全局判决。

## 选择建议

- **先问任务形状，不要先问“哪个更先进”。**
- 需要全局排队、统一优先级、确定性流水线 → `classic`。
- 需要连续上下文、现场改向、单点突破 → `swarm`，并优先从**单 peer** 开始。
- 只有当某个方向明显可并行、且交接能带够证据时，再裂变出第二个 peer。

## 常见误区

- **“swarm 就是多 Agent”**：不是。单 peer 的 swarm 是合法的连续单 Agent。
- **“决策者架构是旧版，蜂群架构是升级版”**：不是。两者是并行架构，按任务形状选择。
- **“图就是事实”**：图是导航与共享记忆；原始事实以 Fact + Evidence 为准。负向结论尤其要能回到请求、参数来源和范围。
- **“multi-peer 一定更快”**：并行收益可能被交接损失、重复探索和共识失效抵消。
